# 实时看板派件情况新增“非标退回”设计方案

## 1. 文档信息

| 项目 | 内容 |
| --- | --- |
| 文档名称 | 实时看板派件情况新增“非标退回”设计方案 |
| 适用模块 | 实时看板 / 派件作业 / 司机监控地图 / 派件明细 |
| 文档状态 | 待评审 |
| 核心变更 | 应派件结果由三种扩展为四种，新增“非标退回” |
| 已确认规则 | 非标退回不计入日清率 |
| 技术基线 | Next.js App Router、React、TypeScript、Tailwind CSS v4、shadcn/ui、ECharts |

## 2. 背景

当前实时看板将应派件的派件结果划分为：

- 待派件
- 已签收
- 派送异常

实际业务中，待派件除了转为已签收或派送异常，还可能在未登记派送异常的情况下直接退回站点。现有模型无法单独记录和展示这类包裹，容易造成以下问题：

- 待派件数量下降，但已签收和派送异常没有对应增加，结果合计无法解释。
- 直接退回与“派送异常后退回”混在一起，无法区分操作是否合规。
- 站点、司机和运单三个层级的数据无法形成一致的追溯链路。
- 如果简单把直接退回视为日清完成，会错误抬高日清率。

因此需要增加独立的“非标退回”派件结果，并在总览、司机监控、地图、明细、筛选、导出和数据接口中保持一致。

## 3. 设计目标

### 3.1 业务目标

1. 独立统计从待派件直接退回站点的包裹。
2. 保证任意统计范围内，应派件数量与四种派件结果严格核平。
3. 保持日清率原有业务含义，非标退回不进入日清完成量。
4. 能从站点汇总下钻到司机，再下钻到具体运单和退回凭证。
5. 明确区分“非标退回”和“派送异常后的退回流程”。

### 3.2 产品目标

1. 用户在派件作业区域第一眼能够看到非标退回数量。
2. 用户不会因图表或进度条设计而误认为非标退回提升了日清率。
3. 四种结果在总览、详情、筛选、地图和导出中的名称、顺序和颜色身份一致。
4. 新增状态不破坏现有应派件来源、妥投异常和问题件分析能力。

### 3.3 非目标

本次不包含以下内容：

- 重构站点交取件的完整退件业务流程。
- 修改派送异常问题件的认定规则。
- 将非标退回计入日清率或妥投率。
- 新增司机侧发起退回的操作页面。
- 调整实时看板之外的考核规则，除非这些规则直接读取本次变更的派件状态。

## 4. 术语和边界

| 术语 | 定义 | 是否为派件结果 | 是否计入日清率分子 |
| --- | --- | --- | --- |
| 应派件 | 当前统计范围内需要产生派件结果的全部包裹 | 否，统计全集 | 分母 |
| 待派件 | 尚未形成有效派件结果的包裹 | 是 | 否 |
| 已签收 | 已完成正常签收的包裹 | 是 | 是 |
| 派送异常 | 已尝试派送但失败，并按问题件流程登记异常的包裹 | 是 | 是 |
| 非标退回 | 未登记派送异常，直接完成站点退回入库的应派件包裹 | 是 | 否 |
| 待退回 | 已进入退回流程但尚未完成站点入库的包裹 | 否，退回流程状态 | 否 |
| 已退回 | 已完成站点退回入库的流程状态 | 否，退回流程状态 | 取决于其派件结果 |

### 4.1 关键边界

“非标退回”是派件结果；“待退回/已退回”是退回流程状态。二者属于不同维度，不能共用一个布尔字段表达。

以下两种情况必须区分：

```text
正常异常退回：待派件 → 派送异常 → 待退回 → 已退回
非标直接退回：待派件 → 非标退回（站点已入库）
```

第一种仍计入“派送异常”，不计入“非标退回”；第二种只计入“非标退回”，不计入“派送异常”。同一运单在同一统计时点只能归属一个派件结果。

## 5. 指标口径

### 5.1 核心等式

```text
应派件 = 待派件 + 已签收 + 派送异常 + 非标退回
```

四种结果必须互斥，且合计必须等于应派件。

### 5.2 日清率

```text
日清率 =（已签收 + 派送异常）÷ 应派件 × 100%
```

非标退回不计入日清率分子。因此，日清率不能再通过 `1 - 待派件率` 推导。

```text
未计入日清量 = 待派件 + 非标退回
日清缺口 = 应派件 - 已签收 - 派送异常
```

### 5.3 妥投率

```text
妥投率 = 已签收 ÷ 应派件 × 100%
```

如果页面展示的是 2400 妥投率，则沿用当前“当期应派”口径：

```text
2400 妥投率 = 当期应派中已签收数量 ÷ 当期应派 × 100%
```

非标退回不计入妥投量，也不从分母中剔除。

### 5.4 非标退回率

```text
非标退回率 = 非标退回 ÷ 应派件 × 100%
```

非标退回率用于解释结果构成和识别流程异常，不参与日清率计算。

### 5.5 计算精度

- 数量使用整数。
- 比率由数量实时计算，不接受前端独立配置的硬编码百分比。
- 页面统一保留两位小数。
- 分母为 0 时展示 `0.00%`，不得出现 `NaN` 或 `Infinity`。
- 四项结果百分比因四舍五入可能合计为 `99.99%` 或 `100.01%`，数量仍是核平的唯一依据。

### 5.6 示例

假设某统计范围内：

| 指标 | 数量 |
| --- | ---: |
| 应派件 | 1,781 |
| 待派件 | 281 |
| 已签收 | 1,378 |
| 派送异常 | 102 |
| 非标退回 | 20 |

则：

```text
结果核平：281 + 1,378 + 102 + 20 = 1,781
日清率：(1,378 + 102) ÷ 1,781 = 83.10%
妥投率：1,378 ÷ 1,781 = 77.37%
非标退回率：20 ÷ 1,781 = 1.12%
未计入日清量：281 + 20 = 301
```

当 20 件包裹从待派件转为非标退回时，待派件减少 20，非标退回增加 20，应派件不变，日清率不变。

## 6. 状态模型

### 6.1 派件结果枚举

建议统一采用稳定的机器值和独立展示文案：

| 机器值 | 中文文案 |
| --- | --- |
| `pending` | 待派件 |
| `delivered` | 已签收 |
| `exception` | 派送异常 |
| `nonstandard_return` | 非标退回 |

不要在不同页面分别维护中文联合类型、英文联合类型和状态映射。建议抽取单一领域类型和展示映射，供总览、地图、详情、导出共同使用。

### 6.2 状态转换

```text
                         ┌──────────→ 已签收
                         │
应派件进入待派件 ────────┼──────────→ 派送异常 ──→ 待退回/已退回
                         │
                         └──────────→ 非标退回
```

允许的业务转换：

- `pending → delivered`
- `pending → exception`
- `pending → nonstandard_return`

状态纠错不直接覆盖历史记录，应通过具有操作人、操作时间和原因的更正事件完成，并重新生成当前快照。

### 6.3 非标退回认定时点

推荐以“站点退回入库扫描成功”为非标退回生效时点，需同时满足：

1. 运单属于当前或历史应派件。
2. 当前派件结果为待派件。
3. 没有有效的派送异常记录。
4. 站点已完成退回入库扫描。

司机仅发起退回、包裹仍在途中时，不应提前计入非标退回；此时应继续保留待派件结果，并由退回流程记录处理中状态。

### 6.4 去重规则

- 每个运单在一个派件周期中只能存在一个当前派件结果。
- 相同入库扫描事件重复上报时必须幂等。
- 已签收或已登记派送异常的运单，不能通过普通扫描直接变成非标退回。
- 需要纠错时必须记录原状态、目标状态、原因、操作人和操作时间。

## 7. 信息架构

采用当前数据看板的页面配方：

```text
页面头部
  └─ 工作模式与刷新控制
      └─ 生命周期摘要卡
          └─ 派件作业摘要
              ├─ 应派件/待派件/非标退回/日清率/2400妥投率
              └─ 展开详情
                  ├─ 派件结果分布
                  ├─ 指标口径说明
                  └─ 司机派件情况
                      └─ 司机监控地图与运单列表
```

“派件结果分布”和“日清进度”必须作为两个不同的信息概念呈现：

- 派件结果分布：四种结果合计 100%。
- 日清进度：只计算已签收和派送异常，非标退回位于未计入日清的一侧。

## 8. 总览设计

### 8.1 派件作业摘要卡

现有摘要卡增加非标退回，推荐结构：

```text
┌──────────────────────────────────────────────────────────────┐
│ 派件作业                                                     │
│                                                              │
│ 应派件        待派件        非标退回       日清率   2400妥投率 │
│ 1,781         281           20            83.10%   77.37%    │
│ 当期应派1,657                              圆环      圆环      │
└──────────────────────────────────────────────────────────────┘
```

交互要求：

- 应派件、待派件和非标退回数量均可点击进入对应明细。
- 日清率 Tooltip 固定展示公式，并列出已签收、派送异常、待派件、非标退回的数量。
- 非标退回为 0 时仍展示 `0`，不隐藏指标，防止用户误以为功能未生效。
- 刷新时所有数量和比率使用同一批次快照，避免短时间内无法核平。

### 8.2 日清率圆环

日清率圆环只表达两类：

| 分段 | 构成 | 视觉 |
| --- | --- | --- |
| 已计入日清 | 已签收 + 派送异常 | 主进度色 |
| 未计入日清 | 待派件 + 非标退回 | 中性剩余色 |

圆环中心展示日清率，辅助技术文案示例：

```text
日清率 83.10%，已计入日清 1,480 件，未计入日清 301 件；其中待派件 281 件，非标退回 20 件。
```

圆环不使用四种派件结果的四段颜色，避免将结果分布和日清率混为一个概念。

### 8.3 派件结果分布

展开后的派件结果区域调整为四段完整构成：

```text
┌──────────────────────────────────────────────────────────────┐
│ 派件结果分布                         全部｜当期应派｜历史未派 │
│ ████████████████████████████████████████████████████████████ │
│                                                              │
│ 待派件          已签收          派送异常         非标退回     │
│ 281 / 15.78%    1,378 / 77.37%  102 / 5.73%     20 / 1.12%  │
└──────────────────────────────────────────────────────────────┘
```

设计要求：

- 四段条宽度由各结果数量除以当前范围的应派件计算。
- 四段均提供可点击的键盘焦点入口。
- 不能只靠颜色区分，必须同时展示名称、数量和比例。
- 顺序在指标卡、图例、筛选和表格中保持一致：待派件、已签收、派送异常、非标退回。
- 当某项为 0 时，分段可以不可见，但下方指标仍保留并显示 `0 / 0.00%`。
- 点击分段或指标进入相同的明细结果。

### 8.4 指标说明区域

指标说明更新为：

```text
应派件 = 当期应派 + 历史未派
应派件 = 待派件 + 已签收 + 派送异常 + 非标退回
日清率 =（已签收 + 派送异常）÷ 应派件 × 100%
未计入日清量 = 待派件 + 非标退回
```

新增定义：

> 非标退回：应派件中未登记派送异常，直接完成站点退回入库的快递；不计入日清率。

这是影响业务判断的核心信息，应直接展示在指标说明中，不只放在 Tooltip 内。

## 9. 司机派件情况设计

### 9.1 司机卡片

司机结果区域由三项扩展为四项：

```text
已签收 | 派送异常 | 非标退回 | 待派件
```

每项展示数量和占该司机应派件的比例。司机卡片中的“完成进度”统一改为“日清进度”，计算公式保持：

```text
司机日清率 =（司机已签收 + 司机派送异常）÷ 司机应派件 × 100%
```

非标退回不进入进度条的已完成部分。为了避免剩余空白被误解为纯待派件，进度条旁应明确展示：

```text
未计入日清：待派件 N + 非标退回 M
```

桌面端四项横向排列；空间不足时使用 `2 × 2` 网格。移动端不缩小字号。

### 9.2 司机列表排序

在现有排序能力之外，增加：

- 非标退回量从高到低
- 非标退回量从低到高

排序对当前已提交的筛选结果生效，选择后立即执行并回到第 1 页。

### 9.3 司机汇总条

司机监控详情的指标汇总按两个组展示：

```text
结果数量：应派件｜待派件｜已签收｜派送异常｜非标退回
效率指标：妥投率｜日清率
```

如果横向空间不足，允许指标区域自身横向滚动；不得造成页面整体横向滚动。

## 10. 司机监控地图设计

### 10.1 地图标记

新增 `nonstandard_return` 地图状态。地图标记、运单卡片左侧状态线和图例使用相同颜色身份。

推荐状态视觉：

| 状态 | 建议颜色角色 | 说明 |
| --- | --- | --- |
| 待派件 | 中性或现有待派件色 | 尚未产生结果 |
| 已签收 | `delivery-delivered` / 青绿 | 正常成功 |
| 派送异常 | `delivery-exception` / 琥珀或异常语义色 | 派送失败 |
| 非标退回 | 新增 `delivery-nonstandard-return` / 低饱和紫色 | 与异常、品牌色区分 |

颜色只能通过 `src/app/globals.css` 的语义 token 提供。禁止在业务组件中直接写 Hex 值，禁止使用 GOFO 品牌橙作为该状态色。

### 10.2 地图定位逻辑

- 待派件优先显示目的地址位置。
- 已签收和派送异常沿用当前采集位置规则。
- 非标退回优先显示实际退回站点坐标。
- 退回站点坐标缺失时，可回退到最后有效采集位置；仍缺失时不绘制地图点，并在列表中保留运单。
- Tooltip 或卡片明确展示“退回站点”和“退回时间”，不得通过地图位置让用户自行推断。

### 10.3 地图筛选和图例

- 派件状态筛选增加“非标退回”。
- 图例固定展示四种状态，即使当前筛选结果中某状态数量为 0。
- 地图标记的 `aria-label` 包含编号、运单号和“非标退回”状态。
- 状态选择后，同时过滤地图点和左侧运单列表。

## 11. 下钻详情设计

### 11.1 新增详情类型

新增独立详情类型：

```ts
nonstandard-return
```

详情标题为“非标退回”，与应派件、待派件、已签收和派送异常保持相同的进入、返回和 URL 状态恢复方式。

### 11.2 司机视图

推荐字段：

| 字段 | 说明 | 是否可排序 |
| --- | --- | --- |
| 司机 | 司机名称 | 否 |
| 应派件 | 当前范围内应派件总量 | 是 |
| 非标退回 | 非标退回数量 | 是 |
| 非标退回率 | 非标退回 ÷ 应派件 | 是 |
| 当期应派非标退回 | 来源为当期应派的数量 | 是 |
| 历史未派非标退回 | 来源为历史未派的数量 | 是 |
| 最近退回时间 | 最近一次退回入库时间 | 是 |
| 操作 | 联系司机 | 否，固定右侧 |

点击任意非标退回数量进入该司机的运单视图。

### 11.3 运单视图

推荐字段：

| 字段 | 说明 |
| --- | --- |
| 运单编号 | 可点击进入运单详情 |
| 运单状态 | 非标退回 |
| 派件来源 | 当期应派或历史未派 |
| 领件时间 | 原始领件时间 |
| 司机 | 当前责任司机 |
| 路区 | 司机路区 |
| 邮编 | 运单邮编 |
| 快递员路线 | 运单路线 |
| 退回原因 | 非标退回原因 |
| 退回站点 | 完成入库的站点 |
| 退回时间 | 站点入库时间 |
| 最新操作 | 如“非标退回入库” |
| 操作时间 | 最新操作时间 |
| 操作人 | 站点扫描操作人 |

表格使用项目 `Table variant="grid"`。筛选、表格、结果数和分页必须处于同一个有边框、无阴影的数据区域内。

### 11.4 查询条件

高频条件：

- 司机
- 完整运单编号
- 派件来源
- 退回原因

低频条件可放入“更多条件”：

- 退回站点
- 退回时间范围
- 路区
- 邮编

查询后回到第 1 页；重置清除全部条件；导出基于已提交条件，不读取尚未查询的草稿条件。

### 11.5 应派件详情调整

应派件详情中的派件状态多选调整为：

```text
待派件、已签收、派送异常、非标退回
```

司机视图增加“非标退回”列，且满足：

```text
司机应派件 = 司机待派件 + 司机已签收 + 司机派送异常 + 司机非标退回
```

### 11.6 运单详情 Sheet

当状态为非标退回时，运单详情增加“退回信息”区块：

- 退回类型：非标退回
- 退回原因
- 退回站点
- 退回入库时间
- 退回操作人
- 关联扫描记录或凭证

该内容属于多区块详情，继续使用现有 `Sheet`，不新增 Dialog。

## 12. 视觉规范

## 15. 数据结构建议

### 15.1 汇总结构

```ts
type DeliverySummary = {
  total: number
  pending: number
  delivered: number
  exception: number
  nonStandardReturn: number
  pendingRate: number
  deliveredRate: number
  exceptionRate: number
  nonStandardReturnRate: number
  clearanceRate: number
}
```

其中：

```text
clearanceRate = (delivered + exception) / total
```

推荐后端返回数量，前后端共享统一计算函数或由后端返回经过校验的比率。禁止数量和比率由两套独立配置维护。

### 15.2 运单结构

```ts
type DeliveryStatus =
  | "pending"
  | "delivered"
  | "exception"
  | "nonstandard_return"

type NonstandardReturnInfo = {
  returnedAt: string
  stationId: string
  stationName: string
  reasonCode: string
  reasonLabel: string
  operatorId: string
  operatorName: string
  scanEventId: string
}
```

时间点使用含时区的 ISO 8601。页面展示通过共享 formatter 格式化为用户时区下的 `MM/DD/YYYY HH:mm`。

### 15.3 原因字典

建议原因使用稳定编码和可配置文案，例如：

| 原因编码 | 展示文案 |
| --- | --- |
| `NO_EXCEPTION_RECORD` | 未登记异常直接退回 |
| `WRONG_OPERATION` | 操作流程不规范 |
| `STATION_RECALL` | 站点临时召回 |
| `OTHER` | 其他 |

最终字典应由业务确认；前端不得依赖中文文案进行判断。

## 16. API 契约建议

### 16.1 总览接口

返回全部、当期应派和历史未派三个范围的真实汇总，禁止使用全局比例推算子范围：

```json
{
  "delivery": {
    "all": {
      "total": 1781,
      "pending": 281,
      "delivered": 1378,
      "exception": 102,
      "nonStandardReturn": 20,
      "clearanceRate": 83.10
    },
    "current": {},
    "history": {}
  },
  "snapshotAt": "2026-08-21T16:42:18-04:00"
}
```

### 16.2 司机汇总接口

每名司机返回四状态数量、日清率和非标退回率。接口返回前执行核平校验：

```text
total === pending + delivered + exception + nonStandardReturn
```

### 16.3 运单列表接口

状态查询参数接受：

```text
pending,delivered,exception,nonstandard_return
```

非标退回详情查询支持司机、运单号、来源、退回原因、站点和时间范围。

### 16.4 兼容策略

- 后端上线初期若字段缺失，前端可临时按 `0` 兼容，但应记录契约告警。
- 兼容期结束后将 `nonStandardReturn` 设为必填，避免长期掩盖接口缺陷。
- 老版本客户端忽略新增字段时，后端仍保持既有字段含义不变。
- 不把非标退回并入 `exception` 以兼容旧客户端，否则会污染日清率和异常分析。

## 17. 数据质量与实时性

### 17.1 核平校验

每个统计范围、站点、司机均执行：

```text
应派件 - 待派件 - 已签收 - 派送异常 - 非标退回 = 0
```

校验失败时：

- 不使用差额自动填充待派件。
- 记录数据质量告警和快照时间。
- 页面保留上一份已核平快照，或明确显示“数据暂未核平”。

### 17.2 同批快照

总览、图表和司机列表应读取相同 `snapshotAt` 的数据。不能分别请求后直接拼接，否则状态正在变化时会产生瞬时差额。

### 17.3 历史回溯

- 上线前历史数据无法准确识别时，不建议把已有 `returned=true` 的异常件批量回填为非标退回。
- 只有能够证明“未登记异常且已直接入库”的历史事件才能回填。
- 无法确认的历史记录保持原状态，并从功能上线时点开始准确统计。

## 21. 验收标准

### 21.1 必须满足

1. 应派件结果完整展示为待派件、已签收、派送异常、非标退回。
2. 任意统计范围满足四项之和等于应派件。
3. 日清率严格等于 `(已签收 + 派送异常) ÷ 应派件`。
4. 待派件转为非标退回时，日清率不得变化。
5. 非标退回不进入妥投率、派送异常量和问题件原因分布。
6. 非标退回与派送异常后退回不重复计数。
7. 总览、司机、地图、运单明细和导出的数量一致。
8. 非标退回支持独立下钻、筛选和导出。
9. 全部、当期应派、历史未派均使用真实数量，不按总比例估算。
10. 页面通过桌面端和 390 × 844 移动端检查。

### 21.2 发布前检查

- 产品确认非标退回认定事件和原因字典。
- 后端确认状态互斥、幂等和核平策略。
- 数据团队确认历史数据是否具备可靠回填条件。
- 前端确认语义 token、状态顺序和可访问文案。
- 测试确认日清率排除非标退回的所有路径。
- 执行 `pnpm lint` 和 `pnpm build`。

## 22. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 把现有 `returned` 字段当成非标退回 | 异常件被重复统计 | 使用独立派件状态和独立退回信息结构 |
| 前后端分别计算不同公式 | 日清率不一致 | 固化公式并使用契约测试 |
| 子范围按总比例估算 | 当期和历史数据无法核平 | 接口直接返回各范围真实数量 |
| 异步刷新导致总览和明细快照不同 | 用户看到瞬时差额 | 所有模块携带并使用同一 `snapshotAt` |
| 历史数据强行回填 | 错误制造非标退回记录 | 只有证据充分的事件才回填 |
| 非标退回颜色过度警示 | 与派送异常混淆 | 使用独立低饱和紫色，并始终配合文字 |
| 日清进度剩余部分被理解为待派件 | 忽略非标退回影响 | 直接展示“未计入日清 = 待派件 + 非标退回” |

## 23. 最终决策摘要

本方案采用以下最终规则：

```text
1. 非标退回是应派件的独立、互斥派件结果。
2. 应派件 = 待派件 + 已签收 + 派送异常 + 非标退回。
3. 日清率 =（已签收 + 派送异常）÷ 应派件。
4. 非标退回不计入日清率和妥投率。
5. 待派件转为非标退回时，日清率保持不变。
6. 非标退回与派送异常后的退回流程分开建模、分开统计。
7. 派件结果分布和日清进度使用两个不同的视觉表达。
```
