# 实时看板派件情况新增“非标退回”设计方案

## 1. 文档信息

| 项目 | 内容 |
| --- | --- |
| 文档名称 | 实时看板派件情况新增“非标退回”设计方案 |
| 适用模块 | 实时看板 / 派件作业 / 司机监控地图 / 派件明细 |
| 文档状态 | 待评审 |
| 核心变更 | 应派件结果由三种扩展为四种，新增“非标退回” |
| 已确认规则 | 非标退回不计入日清率 |
| 技术基线 | Next.js App Router、React、TypeScript、Tailwind CSS v4、shadcn/ui、ECharts |

## 2. 背景

当前实时看板将应派件的派件结果划分为：

- 待派件
- 已签收
- 派送异常

实际业务中，待派件除了转为已签收或派送异常，还可能在未登记派送异常的情况下直接退回站点。现有模型无法单独记录和展示这类包裹，容易造成以下问题：

- 待派件数量下降，但已签收和派送异常没有对应增加，结果合计无法解释。
- 直接退回与“派送异常后退回”混在一起，无法区分操作是否合规。
- 站点、司机和运单三个层级的数据无法形成一致的追溯链路。
- 如果简单把直接退回视为日清完成，会错误抬高日清率。

因此需要增加独立的“非标退回”派件结果，并在总览、司机监控、地图、明细、筛选、导出和数据接口中保持一致。

## 3. 设计目标

### 3.1 业务目标

1. 独立统计从待派件直接退回站点的包裹。
2. 保证任意统计范围内，应派件数量与四种派件结果严格核平。
3. 保持日清率原有业务含义，非标退回不进入日清完成量。
4. 能从站点汇总下钻到司机，再下钻到具体运单和退回凭证。
5. 明确区分“非标退回”和“派送异常后的退回流程”。

### 3.2 产品目标

1. 用户展开派件作业详情后，能够在派件结果分布中直接看到非标退回数量。
2. 用户不会因图表或进度条设计而误认为非标退回提升了日清率。
3. 四种结果在总览、详情、筛选、地图和导出中的名称、顺序和颜色身份一致。
4. 新增状态不破坏现有应派件来源、妥投异常和问题件分析能力。

### 3.3 非目标

本次不包含以下内容：

- 重构站点交取件的完整退件业务流程。
- 修改派送异常问题件的认定规则。
- 将非标退回计入日清率或妥投率。
- 新增司机侧发起退回的操作页面。
- 调整实时看板之外的考核规则，除非这些规则直接读取本次变更的派件状态。

## 4. 术语和边界

| 术语 | 定义 | 是否为派件结果 | 是否计入日清率分子 |
| --- | --- | --- | --- |
| 应派件 | 当前统计范围内需要产生派件结果的全部包裹 | 否，统计全集 | 分母 |
| 待派件 | 尚未形成有效派件结果的包裹 | 是 | 否 |
| 已签收 | 已完成正常签收的包裹 | 是 | 是 |
| 派送异常 | 已尝试派送但失败，并按问题件流程登记异常的包裹 | 是 | 是 |
| 非标退回 | 未登记派送异常，直接完成站点退回入库的应派件包裹 | 是 | 否 |
| 待退回 | 已进入退回流程但尚未完成站点入库的包裹 | 否，退回流程状态 | 否 |
| 已退回 | 已完成站点退回入库的流程状态 | 否，退回流程状态 | 取决于其派件结果 |

### 4.1 关键边界

“非标退回”是派件结果；“待退回/已退回”是退回流程状态。二者属于不同维度，不能共用一个布尔字段表达。

以下两种情况必须区分：

```text
正常异常退回：待派件 → 派送异常 → 待退回 → 已退回
非标直接退回：待派件 → 非标退回（站点已入库）
```

第一种仍计入“派送异常”，不计入“非标退回”；第二种只计入“非标退回”，不计入“派送异常”。同一运单在同一统计时点只能归属一个派件结果。

## 5. 指标口径

### 5.1 核心等式

```text
应派件 = 待派件 + 已签收 + 派送异常 + 非标退回
```

四种结果必须互斥，且合计必须等于应派件。

### 5.2 日清率

```text
日清率 =（已签收 + 派送异常）÷ 应派件 × 100%
```

非标退回不计入日清率分子。因此，日清率不能再通过 `1 - 待派件率` 推导。

```text
未计入日清量 = 待派件 + 非标退回
日清缺口 = 应派件 - 已签收 - 派送异常
```

### 5.3 妥投率

```text
妥投率 = 已签收 ÷ 应派件 × 100%
```

如果页面展示的是 2400 妥投率，则沿用当前“当期应派”口径：

```text
2400 妥投率 = 当期应派中已签收数量 ÷ 当期应派 × 100%
```

非标退回不计入妥投量，也不从分母中剔除。

### 5.4 非标退回率

```text
非标退回率 = 非标退回 ÷ 应派件 × 100%
```

非标退回率用于解释结果构成和识别流程异常，不参与日清率计算。

### 5.5 百分比统一处理规则

数量使用整数，比率由数量实时计算，不接受前端独立配置的硬编码百分比。所有百分比统一保留两位小数。

对于“待派件、已签收、派送异常、非标退回”这类互斥且完整、理论合计为 100% 的构成组，统一采用“最小项补差”规则：

1. 先使用未四舍五入的原始占比，将所有非零项目按占比从大到小排列；数量为 0 的项目固定显示 `0.00%`，不承担补差。
2. 除最后一项外，其余项目按标准四舍五入保留两位小数。
3. 最后一项，即原始占比最小的非零项目，不执行普通四舍五入。
4. 最后一项显示值使用 `100.00% - 其余项目显示占比之和` 计算。
5. 最终四项显示占比必须严格合计为 `100.00%`。
6. 补差只影响展示百分比，不修改数量、原始比率或业务状态。

计算顺序和界面顺序分离：计算时临时按原始占比降序排列以确定最小项，计算完成后再映射回固定业务顺序展示。页面、图例、筛选和表格中的状态位置不会因实时数据大小变化而跳动。

固定业务展示顺序仍为：

```text
已签收 → 派送异常 → 非标退回 → 待派件
```

同占比时使用上述固定业务顺序作为稳定排序依据，排在后面的同值项承担补差。这样相同数据在服务端、浏览器和导出中会得到相同结果。

实现时建议使用“百分比基点”整数计算，避免 JavaScript 浮点误差：

```text
100.00% = 10,000 个百分比基点
普通项基点 = 四舍五入（项目数量 ÷ 总数量 × 10,000）
最小项基点 = 10,000 - 其余项目基点之和
显示百分比 = 基点 ÷ 100
```

边界规则：

- 分母为 0 时，所有项目均展示 `0.00%`，不执行补差，不得出现 `NaN` 或 `Infinity`。
- 数量为 0 的项目固定展示 `0.00%`，不参与补差候选；由原始占比最小的非零项目承担差值，避免出现“数量为 0、占比却为 0.01%”的错误表达。
- 若极端舍入组合导致最小项补差结果小于 `0.00%`，则将该项固定为 `0.00%`，差值转由次小的正数项承担，依次向上处理；任何项目不得展示负百分比。
- 日清率、妥投率等不属于同一完整构成组的独立指标，仍单独按标准四舍五入保留两位小数，不参与四项结果的 100% 补差。

示例：四项数量为 `5、3、2、1`，总数为 `11`。

| 排名 | 原始占比 | 处理方式 | 显示占比 |
| --- | ---: | --- | ---: |
| 1 | 45.4545…% | 正常四舍五入 | 45.45% |
| 2 | 27.2727…% | 正常四舍五入 | 27.27% |
| 3 | 18.1818…% | 正常四舍五入 | 18.18% |
| 4（最小项） | 9.0909…% | `100.00% - 45.45% - 27.27% - 18.18%` | 9.10% |

最终显示合计为 `100.00%`。

### 5.6 示例

假设某统计范围内：

| 指标 | 数量 |
| --- | ---: |
| 应派件 | 1,781 |
| 待派件 | 281 |
| 已签收 | 1,378 |
| 派送异常 | 102 |
| 非标退回 | 20 |

则：

```text
结果核平：281 + 1,378 + 102 + 20 = 1,781
日清率：(1,378 + 102) ÷ 1,781 = 83.10%
妥投率：1,378 ÷ 1,781 = 77.37%
非标退回率：20 ÷ 1,781 = 1.12%
未计入日清量：281 + 20 = 301
```

该示例中，非标退回是四项结果中的最小项，其显示占比应由 `100.00%` 减去待派件、已签收和派送异常的显示占比得到。本组数据的补差结果仍为 `1.12%`。

当 20 件包裹从待派件转为非标退回时，待派件减少 20，非标退回增加 20，应派件不变，日清率不变。

## 6. 状态模型

### 6.1 派件结果枚举

建议统一采用稳定的机器值和独立展示文案：

| 机器值 | 中文文案 |
| --- | --- |
| `pending` | 待派件 |
| `delivered` | 已签收 |
| `exception` | 派送异常 |
| `nonstandard_return` | 非标退回 |

不要在不同页面分别维护中文联合类型、英文联合类型和状态映射。建议抽取单一领域类型和展示映射，供总览、地图、详情、导出共同使用。

### 6.2 状态转换

```text
                         ┌──────────→ 已签收
                         │
应派件进入待派件 ────────┼──────────→ 派送异常 ──→ 待退回/已退回
                         │
                         └──────────→ 非标退回
```

允许的业务转换：

- `pending → delivered`
- `pending → exception`
- `pending → nonstandard_return`

状态纠错不直接覆盖历史记录，应通过具有操作人、操作时间和原因的更正事件完成，并重新生成当前快照。

### 6.3 非标退回认定时点

推荐以“站点退回入库扫描成功”为非标退回生效时点，需同时满足：

1. 运单属于当前或历史应派件。
2. 当前派件结果为待派件。
3. 没有有效的派送异常记录。
4. 站点已完成退回入库扫描。

司机仅发起退回、包裹仍在途中时，不应提前计入非标退回；此时应继续保留待派件结果，并由退回流程记录处理中状态。

### 6.4 去重规则

- 每个运单在一个派件周期中只能存在一个当前派件结果。
- 相同入库扫描事件重复上报时必须幂等。
- 已签收或已登记派送异常的运单，不能通过普通扫描直接变成非标退回。
- 需要纠错时必须记录原状态、目标状态、原因、操作人和操作时间。

## 7. 信息架构

采用当前数据看板的页面配方：

```text
页面头部
  └─ 工作模式与刷新控制
      └─ 生命周期摘要卡
          └─ 派件作业摘要
              ├─ KPI 保持现状：应派件/待派件/日清率/2400妥投率
              └─ 展开详情（新增非标退回）
                  ├─ 派件结果分布
                  ├─ 指标口径说明
                  └─ 司机派件情况
                      └─ 司机监控地图与运单列表
```

“派件结果分布”和“日清进度”必须保持两套独立的计算语义，但允许在日清率复合圆环中叠加呈现：

- 圆环分段表达派件结果分布：已签收、派送异常、非标退回、待派件四种结果合计 `100.00%`。
- 圆环中心表达日清进度：只计算已签收和派送异常，非标退回不计入日清率。
- 复杂 Tooltip 同时展示两套口径，并明确给出日清率公式，不能用圆环分段之和推导日清率。

## 8. 总览设计

### 8.1 派件作业摘要卡

现有派件作业 KPI 卡片不新增“非标退回”，指标数量和布局保持现状：

```text
┌──────────────────────────────────────────────────────┐
│ 派件作业                                             │
│                                                      │
│ 应派件          待派件          日清率   2400妥投率 │
│ 1,781           281             83.10%   77.37%      │
│ 当期应派1,657                   圆环      圆环        │
└──────────────────────────────────────────────────────┘
```

交互要求：

- 应派件和待派件继续沿用现有点击下钻能力。
- KPI 卡片不新增“非标退回”独立 KPI 或独立下钻入口；非标退回仅作为日清率圆环的一段，并在复杂 Tooltip 中展示明细。
- 非标退回的带标签指标和下钻入口仍统一放在展开后的“派件结果分布”。
- 日清率圆环和复杂 Tooltip 的完整规则见 8.2。
- 刷新时所有数量和比率使用同一批次快照，避免短时间内无法核平。

数据变化规则：待派件转为非标退回后，KPI 卡片中的待派件数量减少，日清率保持不变；日清率圆环中的待派件分段相应缩小、非标退回分段相应增大，展开派件作业详情后可以进行带标签查看和下钻。

### 8.2 日清率圆环

日清率采用复合圆环：圆环分段展示全部派件状态，圆心继续展示日清率，不新增 KPI 卡片。

| 分段顺序 | 状态 | 视觉语义 | 是否计入日清率 |
| --- | --- | --- | --- |
| 1 | 已签收 | 青绿色 `delivery-delivered` | 是 |
| 2 | 派送异常 | 琥珀色 `delivery-exception` | 是 |
| 3 | 非标退回 | 低饱和紫色 `delivery-nonstandard-return` | 否 |
| 4 | 待派件 | 中性灰 `delivery-pending` | 否 |

圆环规则：

- 四个分段的弧长使用 6.2 定义的两位小数显示占比，执行“最小非零项补差”后严格合计为 `100.00%`。
- 分段和 Tooltip 行顺序固定为已签收、派送异常、非标退回、待派件，不按占比大小改变界面位置。
- 中心主值为日清率，例如 `83.10%`；中心辅助标签固定为“日清率”。
- 中心值仍按 `(已签收 + 派送异常) ÷ 应派件` 独立计算并正常四舍五入，不参与四状态构成的补差。
- 非标退回分段仅表示其在应派件结果中的占比，不表示其计入日清。
- 数量为 0 的状态不绘制可见弧段，但复杂 Tooltip 中仍保留该行并显示 `0 件 · 0.00%`。

示意：

```text
             ┌───────────────┐
             │    83.10%     │
             │     日清率     │
             └───────────────┘
圆环四段：已签收 77.37%｜派送异常 5.73%｜非标退回 1.12%｜待派件 15.78%
```

#### 8.2.1 复杂 Tooltip

桌面端悬停圆环任一分段、键盘聚焦圆环，或移动端点击圆环时，展示同一个只读复杂 Tooltip。Tooltip 不只展示当前命中分段，而是展示当前统计范围的完整快照；命中分段对应行使用字重强调。

```text
┌────────────────────────────────┐
│ 派件结果详情                    │
│ 应派件                 1,781 件 │
│ ● 已签收      1,378 件 · 77.37% │
│ ● 派送异常      102 件 · 5.73% │
│ ● 非标退回       20 件 · 1.12% │
│ ● 待派件        281 件 · 15.78% │
│ ────────────────────────────── │
│ 日清率                   83.10% │
│（已签收 + 派送异常）÷ 应派件   │
└────────────────────────────────┘
```

Tooltip 展示规则：

- 标题固定为“派件结果详情”，字段依次为应派件、四种状态、日清率和公式说明。
- 四种状态均展示“数量 + 占应派件比例”；比例与圆环使用同一组补差后的显示值。
- 日清率单独成组并在下方显示完整公式，非标退回行标注为“不计入日清”的辅助说明。
- 使用图表 Tooltip 的浮层样式：`popover` 表面、阴影、无边框、`12px` 内边距、`6px` 圆角、最大宽度 `260px`。
- 标题使用 `12px / 500`，字段使用 `12px / 400`；标签使用弱化前景色，数量和比例使用等宽数字并右对齐。
- 颜色仅用于每个状态名称前的 `8px` 圆点；状态名称、数量、比例和“不计入日清”文案共同承担辨识，不能只依赖颜色。
- 采用 ECharts `trigger: "item"`，自定义 formatter 读取完整汇总数据；缺失值显示 `—`，真实 0 值必须显示。
- Tooltip 为只读信息，不放置下钻按钮；下钻继续通过展开后的派件结果指标完成。
- Tooltip 需要进行视口碰撞处理；移动端再次点击空白区域或按 Escape 关闭，不能遮挡卡片中的其他 KPI。

#### 8.2.2 可访问语义

- 圆环容器可获得键盘焦点，聚焦时展示与悬停一致的复杂 Tooltip，并保留项目统一焦点环。
- 圆环的可访问名称应包含日清率、应派件、四状态数量与比例，以及“非标退回不计入日清”的说明。
- 复杂 Tooltip 中的信息必须在展开后的派件结果分布中有等价的常驻文本，不能把关键数据只放在悬浮层中。
- 推荐可访问摘要：`日清率 83.10%；应派件 1,781 件；已签收 1,378 件，占 77.37%；派送异常 102 件，占 5.73%；非标退回 20 件，占 1.12%，不计入日清；待派件 281 件，占 15.78%。`

### 8.3 派件结果分布

展开后的派件结果区域调整为四段完整构成：

```text
┌──────────────────────────────────────────────────────────────┐
│ 派件结果分布                         全部｜当期应派｜历史未派 │
│ ████████████████████████████████████████████████████████████ │
│                                                              │
│ 已签收          派送异常         非标退回         待派件       │
│ 1,378 / 77.37%  102 / 5.73%     20 / 1.12%      281 / 15.78% │
└──────────────────────────────────────────────────────────────┘
```

设计要求：

- 四段条宽度由各结果数量除以当前范围的应派件计算。
- 四项显示占比按“最小项补差”规则处理并严格合计为 `100.00%`；图形分段宽度优先使用同一组处理后的显示占比，确保图形与文案一致。
- 最小项根据原始占比动态确定，但计算结果需要映射回固定业务顺序，不能让指标位置随数据大小变化。
- 四段均提供可点击的键盘焦点入口。
- 不能只靠颜色区分，必须同时展示名称、数量和比例。
- 顺序在指标卡、图例、筛选和表格中保持一致：已签收、派送异常、非标退回、待派件；待派件固定放在最后。
- 当某项为 0 时，分段可以不可见，但下方指标仍保留并显示 `0 / 0.00%`。
- 点击分段或指标进入相同的明细结果。

### 8.4 指标说明区域

指标说明更新为：

```text
应派件 = 当期应派 + 历史未派
应派件 = 待派件 + 已签收 + 派送异常 + 非标退回
日清率 =（已签收 + 派送异常）÷ 应派件 × 100%
未计入日清量 = 待派件 + 非标退回
```

新增定义：

> 非标退回：应派件中未登记派送异常，直接完成站点退回入库的快递；不计入日清率。

这是影响业务判断的核心信息，应直接展示在指标说明中，不只放在 Tooltip 内。

## 15. 数据结构建议

### 15.1 汇总结构

```ts
type DeliverySummary = {
  total: number
  pending: number
  delivered: number
  exception: number
  nonStandardReturn: number
  pendingRate: number
  deliveredRate: number
  exceptionRate: number
  nonStandardReturnRate: number
  clearanceRate: number
}
```

其中：

```text
clearanceRate = (delivered + exception) / total
```

推荐后端返回数量，前后端共享统一计算函数或由后端返回经过校验的比率。禁止数量和比率由两套独立配置维护。

建议增加统一的构成百分比计算结果：

```ts
type DeliveryResultRates = {
  pending: number
  delivered: number
  exception: number
  nonStandardReturn: number
  adjustedStatus: DeliveryStatus | null
}
```

四个比率均为两位小数的展示值，合计必须为 `100.00`；`adjustedStatus` 用于测试、排查和导出一致性，不需要直接显示给用户。分母为 0 时四项均为 `0.00`，`adjustedStatus` 为 `null`。

### 15.2 运单结构

```ts
type DeliveryStatus =
  | "pending"
  | "delivered"
  | "exception"
  | "nonstandard_return"

type NonstandardReturnInfo = {
  returnedAt: string
  stationId: string
  stationName: string
  reasonCode: string
  reasonLabel: string
  operatorId: string
  operatorName: string
  scanEventId: string
}
```

地图使用运单已有的收件人位置字段，推荐统一为：

```ts
type RecipientLocation = {
  latitude: number | null
  longitude: number | null
}
```

`NonstandardReturnInfo` 中不重复保存收件人经纬度，避免地址更新或多份坐标来源导致地图位置不一致。

时间点使用含时区的 ISO 8601。页面展示通过共享 formatter 格式化为用户时区下的 `MM/DD/YYYY HH:mm`。

### 15.3 原因字典

建议原因使用稳定编码和可配置文案，例如：

| 原因编码 | 展示文案 |
| --- | --- |
| `NO_EXCEPTION_RECORD` | 未登记异常直接退回 |
| `WRONG_OPERATION` | 操作流程不规范 |
| `STATION_RECALL` | 站点临时召回 |
| `OTHER` | 其他 |

最终字典应由业务确认；前端不得依赖中文文案进行判断。

## 16. API 契约建议

### 16.1 总览接口

返回全部、当期应派和历史未派三个范围的真实汇总，禁止使用全局比例推算子范围：

```json
{
  "delivery": {
    "all": {
      "total": 1781,
      "pending": 281,
      "delivered": 1378,
      "exception": 102,
      "nonStandardReturn": 20,
      "clearanceRate": 83.10
    },
    "current": {},
    "history": {}
  },
  "snapshotAt": "2026-08-21T16:42:18-04:00"
}
```

### 16.2 司机汇总接口

每名司机返回四状态数量、日清率和非标退回率。接口返回前执行核平校验：

```text
total === pending + delivered + exception + nonStandardReturn
```

如果接口返回四项结果的展示占比，必须使用统一的“最小项补差”算法并保证合计为 `100.00`，同时返回承担补差的 `adjustedStatus`。如果接口只返回数量，则由前端共享工具函数计算；禁止每个组件分别实现舍入逻辑。

### 16.3 运单列表接口

状态查询参数接受：

```text
pending,delivered,exception,nonstandard_return
```

应派件详情查询的状态参数支持 `nonstandard_return`。从非标退回指标进入时，前端直接提交 `status=nonstandard_return`，不调用独立的非标退回详情接口。

用于司机监控地图的运单数据必须返回 `recipientLocation.latitude` 和 `recipientLocation.longitude`。非标退回地图点只读取该收件人位置，不读取退回站点或最后采集位置。

### 16.4 兼容策略

- 后端上线初期若字段缺失，前端可临时按 `0` 兼容，但应记录契约告警。
- 兼容期结束后将 `nonStandardReturn` 设为必填，避免长期掩盖接口缺陷。
- 老版本客户端忽略新增字段时，后端仍保持既有字段含义不变。
- 不把非标退回并入 `exception` 以兼容旧客户端，否则会污染日清率和异常分析。

## 17. 数据质量与实时性

### 17.1 核平校验

每个统计范围、站点、司机均执行：

```text
应派件 - 待派件 - 已签收 - 派送异常 - 非标退回 = 0
```

校验失败时：

- 不使用差额自动填充待派件。
- 记录数据质量告警和快照时间。
- 页面保留上一份已核平快照，或明确显示“数据暂未核平”。

### 17.2 同批快照

总览、图表和司机列表应读取相同 `snapshotAt` 的数据。不能分别请求后直接拼接，否则状态正在变化时会产生瞬时差额。

### 17.3 历史回溯

- 上线前历史数据无法准确识别时，不建议把已有 `returned=true` 的异常件批量回填为非标退回。
- 只有能够证明“未登记异常且已直接入库”的历史事件才能回填。
- 无法确认的历史记录保持原状态，并从功能上线时点开始准确统计。

- 时间字段缺失时展示 `—`，不得展示无效日期。

## 21. 验收标准

### 21.1 必须满足

1. 应派件结果完整展示为已签收、派送异常、非标退回、待派件，待派件固定放在最后。
2. 任意统计范围满足四项之和等于应派件。
3. 日清率严格等于 `(已签收 + 派送异常) ÷ 应派件`。
4. 待派件转为非标退回时，日清率不得变化。
5. 非标退回不进入妥投率、派送异常量和问题件原因分布。
6. 非标退回与派送异常后退回不重复计数。
7. 总览、司机、地图、运单明细和导出的数量一致。
8. 非标退回复用应派件下钻，进入后自动筛选 `nonstandard_return`，并支持在应派件详情中继续筛选和导出。
9. 全部、当期应派、历史未派均使用真实数量，不按总比例估算。
10. 四项派件结果百分比均保留两位小数，最小项承担舍入差值，显示合计严格为 `100.00%`。
11. 百分比计算排序不改变页面固定业务展示顺序。
12. 派件作业 KPI 卡片不新增非标退回独立指标；非标退回作为日清率圆环分段并出现在复杂 Tooltip 中，带标签指标和下钻仍位于展开详情及后续监控页面。
13. 日清率圆环展示全部四种状态，圆心日清率保持原公式；复杂 Tooltip 完整展示应派件、四状态数量及占比、日清率和公式。
14. 页面通过桌面端和 390 × 844 移动端检查。

### 21.2 发布前检查

- 产品确认非标退回认定事件和原因字典。
- 后端确认状态互斥、幂等和核平策略。
- 数据团队确认历史数据是否具备可靠回填条件。
- 前端确认语义 token、状态顺序和可访问文案。
- 测试确认日清率排除非标退回的所有路径。
- 执行 `pnpm lint` 和 `pnpm build`。

## 22. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 把现有 `returned` 字段当成非标退回 | 异常件被重复统计 | 使用独立派件状态和独立退回信息结构 |
| 前后端分别计算不同公式 | 日清率不一致 | 固化公式并使用契约测试 |
| 子范围按总比例估算 | 当期和历史数据无法核平 | 接口直接返回各范围真实数量 |
| 异步刷新导致总览和明细快照不同 | 用户看到瞬时差额 | 所有模块携带并使用同一 `snapshotAt` |
| 历史数据强行回填 | 错误制造非标退回记录 | 只有证据充分的事件才回填 |
| 非标退回颜色过度警示 | 与派送异常混淆 | 使用独立低饱和紫色，并始终配合文字 |
| 四状态圆环被理解为四项均计入日清 | 日清率口径被误读 | 圆心固定标注“日清率”，复杂 Tooltip 分组展示四状态构成和日清率公式，并在非标退回行标注“不计入日清” |
| 极小的非标退回分段难以命中 | 用户无法查看明细 | 圆环整体可聚焦、点击，Tooltip 始终展示全部状态，展开区域保留常驻指标 |
| 收件地址标记被理解为包裹当前位置 | 用户误判非标退回实物位置 | 地图标记的 Tooltip 和可访问名称固定标注“标记位置：收件地址”；卡片和详情 Sheet 不增加专属退回信息展示 |
| 各组件独立四舍五入 | 四项显示占比无法合计 100% | 使用共享“最小项补差”函数，统一服务端、页面和导出结果 |
| 按占比排序直接驱动 UI 顺序 | 实时刷新时指标位置跳动 | 仅计算时排序，展示时映射回固定业务顺序 |

## 23. 最终决策摘要

本方案采用以下最终规则：

```text
1. 非标退回是应派件的独立、互斥派件结果。
2. 应派件 = 待派件 + 已签收 + 派送异常 + 非标退回。
3. 日清率 =（已签收 + 派送异常）÷ 应派件。
4. 非标退回不计入日清率和妥投率。
5. 待派件转为非标退回时，日清率保持不变。
6. 非标退回与派送异常后的退回流程分开建模、分开统计。
7. 日清率使用复合圆环：四个分段展示全部派件状态，圆心展示日清率；复杂 Tooltip 展示应派件、四状态数量及占比、日清率和公式。
8. 四项派件结果百分比保留两位小数，最小非零项使用 100.00% 减去其余项之和得到；数量为 0 的项目固定为 0.00%。
9. 百分比计算时按原始占比从大到小排序，展示时保持“已签收、派送异常、非标退回、待派件”的固定业务顺序，待派件固定放在最后。
10. 派件作业 KPI 卡片保持现有四项，不新增非标退回独立 KPI；非标退回可在日清率圆环及复杂 Tooltip 中查看，带标签指标和下钻从展开详情开始提供。
11. 非标退回地图标记统一渲染在收件人经纬度，不使用退回站点或最后采集位置。
12. 非标退回不新增独立下钻详情，点击后直接复用应派件详情并预置非标退回状态筛选。
13. 司机监控地图运单卡片和运单详情 Sheet 均不新增非标退回的原因、站点、退回时间、操作人等专属信息；保留非标退回状态和既有操作记录。
```
