# 产品需求文档（PRD）撰写标准规范 V1.0

> **适用对象**：产品经理  
> **使用场景**：产品经理撰写PRD，交付开发团队（前端+后端）进行 Spec Design 及 Task 拆解  
> **核心原则**：描述"做什么"和"为什么"，不涉及"用什么技术实现"；前后端逻辑清晰区分但不割裂

---

## 文档头部信息

每篇 PRD 文档顶部需包含以下基本信息，用于版本管理和评审流程追踪。

| 字段 | 说明 |
|------|------|
| 需求名称 | 本次需求的中文名称 |
| 版本号 | v1.0 起始，每次变更递增 |
| 状态 | 草稿 / 评审中 / 已通过 |
| 产品负责人 | 填写姓名 |
| 创建日期 | YYYY-MM-DD |
| 最后更新日期 | YYYY-MM-DD |
| 产品内部评审时间 | YYYY-MM-DD |
| 产品内部评审人 | 主持评审的人 |
| 产品内部参与人 | 参与评审的人员列表 |
| 研发评审时间 | YYYY-MM-DD |
| 研发评审人 | 主持评审的人 |
| 研发参与人 | 参与评审的人员列表 |

**交付物清单：**

| 交付物 | 格式 | 必填 | 说明 |
|--------|------|:----:|------|
| PRD 文档 |  Markdown | ✅ | 定义流程、逻辑、规则、提示内容 |
| 原型 | HTML | ✅ | 单页面截图嵌入PRD，多页面附链接 |

## 一、需求概述

### 1.1 需求背景

描述清楚需求的背景、现状和问题。要求：

- 说明当前业务现状和存在的问题
- 交代清楚为什么要做这件事
- 100-300字为宜，简洁但完整

### 1.2 目标价值 / 影响面

描述清楚需求给关键用户带来的价值和影响：

- 列出2条以上可量化或可感知的业务收益
- 说明影响的用户角色和范围
- 如有预期的量化指标（如效率提升百分比、成本降低幅度），需明确标注

### 1.3 需求涉及端口

- 本次需求涉及的用户页面属于web/app/pda
- web端：PC端
- app端：Android、iOS
- pda端：PAD端

### 2.1 业务场景拆解

以业务场景维度进行拆解，反向校验需求调研与分析过程的完整性，及业务的合理性。此部分同时作为 UAT 验收标准的依据。

**撰写格式：**

| 所属业务环节 | 角色 | 活动/操作 | 要求与规则（业务场景维度） |
|:---:|:---:|:---:|:---|
| `<环节名称>` | `<角色>` | `<操作描述>` | 1. 具体规则说明<br>2. 异常场景处理... |

| 所属业务环节 | 角色 | 活动/操作 | 要求与规则 |
|:---:|:---:|:---:|:---|
| `<上游环节>` | | | （无变更则留空或标注"无影响"）|
| `<下游环节>` | | | |

### 2.2 业务流程图

> 涉及业务流程改动的，该内容**必填**；不涉及流程改动的，可以忽略。

可以使用跨角色全景流程、核心业务流程（正向、逆向）、状态生命周期图、业务模型等进行表述。

### 2.3 系统架构图

> 涉及多系统交互或新增系统模块的，该内容**必填**；单系统内功能迭代可忽略。

描述系统模块划分、服务间的调用关系、数据流向。适用于涉及多系统协作、新增服务、引入外部系统（如AI服务、第三方接口）等场景。

> 涉及系统流程改动的，该内容**必填**；不涉及流程改动的，可以忽略。

可以使用跨系统全景流程、核心数据流程（正向、逆向）等进行表述，重点体现系统间的调用时序和数据流转路径。

`[此处插入系统流程图]`

### 2.5 状态流转图

> 涉及单据/对象状态管理的，该内容**必填**。

定义单据/数据对象的各个状态、状态生命周期、不同状态下的限制规则。状态定义的本质是定义数据规则和边界。

`[此处插入状态流转图]`

### 2.6 技术方案概要（可选）

> 适用于技术驱动型需求（如AI/算法、性能优化、架构重构等），普通业务功能可省略。

当需求涉及较复杂的技术决策时，产品经理需与技术团队对齐后，将关键技术方案共识写入PRD，作为开发实施的前提约束。内容可包括：

- **技术路径选型**：明确采用的技术方案及选型依据
- **POC验证结论**：如有前置验证，记录验证结果和关键数据
- **性能/优化策略**：产品侧提出的优化方向和目标约束

> 注意：此处只记录与产品需求相关的技术共识，不涉及详细的技术实现方案（技术实现由开发团队在Spec Design中细化）。

##### 3.2.1.2【后端逻辑】

**1. 数据处理规则**

每个前端功能都必须要有对应的后端功能，如果没有则此板块留空，针对该功能涉及的后端业务逻辑，逐操作说明：

**2. 数据来源与接口说明**

| `<数据/字段>`  | `<来源说明>` | `<更新机制>` |
|:---:|:---|:---|

### 6.3 敏感信息处理

> 涉及敏感信息场景需特别说明，参考公司安全信息标准，基本标准准则如6.3.1内容所示：
> 产品设计之个人敏感信息安全详细标准准则在`skills/prd-writer-GOFO/references/security-specification.md`文件中。

6.3.1 敏感信息处理
6.3.1.1 数据采集：
  - 遵循“先告知后同意”原则，用户同意前不得收集任何信息；
  - 严禁收集非业务必需的敏感数据；
6.3.1.2 数据使用&展示&导出：
  - 功能列表如无必要不要批量显示敏感信息字段，如果必须需可以点击单行的小眼睛展示单条敏感信息，默认展示的时候是脱敏状态。公司类的数据不做强要求。
  - 个人敏感信息统一不允许导出；如果需要可以通过工单实现。
  - 如果需要查看个人敏感信息，可以通过查看单条数据的详情界面进行单个信息查看；
6.3.1.3 数据存储：
  - 用户密码必须采用不可逆的算法存储；
  - 个人信息在数据库中必须加密存储（如AES-256），严禁明文落库；加密密钥须通过密钥管理服务（apollo）管理，与数据库分开存放。
  - 特别声明：在美国经纬度精确到小数位超过2位(千米差异)的敏感信息属于最高优先级。存储必须加密存储，不允许跨境使用(超美国范围),不允许回传给客户或者第三方供应商.如特殊场景需要需要单独评估。
6.3.1.4 数据传输&跨境：
  - 严禁向受关注国家 / 实体传输、共享、出售批量敏感数据
  - 公网开放的所有系统启用HTTPS+TLS1.2以上版本
6.3.1.5 日志记录：
  - 系统增、删、改、导出、敏感信息查询必须记录操作日志
  - 日志内容包括：操作人 、操作时间 、操作IP、操作对象、操作类型、操作结果；
  - 日志中禁止明文敏感信息
  - 日志保存时间不少于12个月。
6.3.1.6 数据删除：
  - 按照业务需求符合最小必要原则即可，对于受监管交易相关的记录（内部的交易类型判定以及详情的文件，比如14117项目的一些报告和过程记录文件）至少保存10年

### 6.4 业务逻辑与风控
  - 发送短信/邮件必须做到频次限制，避免轰炸和资金损失；
  - 登录接口必须有防暴力破解机制，如登录失败5次锁定账号10分钟；
